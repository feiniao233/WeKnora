# 网络接口中断诊断规程

- 场景 ID：`network-interface-down`
- SOP 版本：`1.0.0`

## 适用范围与必要输入

适用于交换机、路由器、防火墙、服务器网卡等接口从可用变为不可用的只读诊断。告警名称和厂商字段只是线索，以接口状态、资产、拓扑和同一时间窗口内的事件为准。

必须有可唯一定位的告警标识。`resolve_alarm` 返回后必须取得发生时间，以及资产或接口标识；缺失接口标识时可继续查询资产上下文，但不得把推测的接口当作事实。

## 固定调用顺序

1. `resolve_alarm`：传入用户提供的告警 ID 或告警键；记录权威告警 ID、发生/恢复时间、资产、接口、状态和原始告警文本。
2. `get_asset_context`：传入已解析的资产和接口标识；关注设备类型、管理状态、接口归属、接口管理状态和可用的接口状态字段。
3. `get_topology_context`：传入已解析的资产和接口标识；关注对端接口、相邻节点和下游影响范围。拓扑无结果不代表不存在对端。
4. `query_operational_evidence`：传入已解析的资产/接口及以告警时间为中心的系统允许时间窗；查询 `alarms`、`logs`、`metrics`。关注 up/down 切换、设备上线/离线或重启、配置/管理状态变更、错误计数和相邻节点的同期事件。
5. 知识检索：仅在已有运行证据后检索绑定知识库；关键词为“接口 down”、“链路抖动”、“端口状态”、“LLDP”、“设备重启”、“管理关闭”，并以实际设备类型补充关键词。

不得跳过前序步骤、替换为外部操作，或扩大资产、接口和时间范围。工具错误或空结果均记录为缺失信息；除无法取得权威告警外，继续完成其余可执行查询。

## 停止条件

- 无权威告警，或告警无法关联任何资产、接口或可核验的运行证据：停止，结论为 `unknown`。
- 已有运行证据但不足以区分候选原因：停止继续猜测，结论为 `suspected` 或 `ambiguous`。
- 不执行 Ping、端口探测、配置读取以外的刷新、设备操作或变更。

## 候选原因与证据

### 物理链路或对端故障

支持：本端明确 down，且对端接口/设备异常或下游同期失联。反对：对端持续正常、无下游影响，或记录显示本端管理关闭。

### 设备重启或掉电

支持：设备离线、启动/重启日志，或同设备多个接口短时间内同时中断。反对：仅单接口中断，且设备运行状态连续。

### 链路抖动

支持：同一时间窗内多次 up/down 切换。反对：只有一次 down，后续无重复切换。

### 管理关闭或配置变更

支持：变更审计、配置日志或明确管理状态记录。反对：管理状态未变且对端或物理层事件先发生。

### 上游或下游故障传播

支持：拓扑相邻节点先故障，随后当前接口或下游资产告警，且时间顺序一致。反对：时间顺序相反或拓扑关系不成立。

## 人工验证与报告

人工验证：核对现场/网管中的端口管理状态与对端状态；核对变更记录；按拓扑确认受影响链路和恢复时间。验证动作由人工在平台外按既有权限执行，本规程不调用任何外部操作。

报告遵循 `SKILL.md` 的统一报告格式；在摘要标明场景 ID、SOP 版本、权威告警 ID 和观察时间窗。每个候选原因必须带支持与反对证据 ID/时间戳；空结果和工具错误写入“缺失信息”。
