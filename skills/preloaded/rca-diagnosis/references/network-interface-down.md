# 网络接口中断诊断规程

- 场景 ID：`network-interface-down`
- SOP 版本：`1.1.0`

## 适用范围与必要输入

适用于交换机、路由器、防火墙、服务器网卡等接口从可用变为不可用的只读诊断。告警名称和厂商字段只是线索，以接口状态、资产、拓扑和同一时间窗口内的事件为准。

必须有可唯一定位的告警标识。主流程完成 `resolve_alarm` 后必须取得发生时间，以及资产或接口线索；缺失接口线索时仍可使用资产字段查询，但不得把推测的接口当作事实。

## 证据查询

- 前置条件：复用主流程中已解析的告警，不得再次调用 `resolve_alarm`。
- `get_asset_context`、`get_topology_context` 和 `query_operational_evidence` 可在同一轮发起，均只传入已解析告警中工具接受的可用字段。输入不足的查询跳过并记入缺失信息，其余查询继续。
- `get_asset_context`：只用资产标识、名称、地址以及类型和区域摘要核对告警对象，不推断接口归属或管理状态。
- `get_topology_context`：只用资产所在节点、拓扑资产数等摘要判断是否存在可用的粗粒度拓扑背景，不推断对端接口或具体链路。
- `query_operational_evidence`：传入已解析告警组成的 `alarm`，以 `alarms`、`logs`、`metrics` 为 `kinds`。观察窗口由服务端固定为告警前后 30 分钟；关注返回告警和日志中的状态切换、离线、重启或变更记录，以及指标中的接口名称或索引、入出方向值、接口速率和入出丢弃。
- 知识检索可选。仅在需要解释设备语义、指标含义、阈值、策略或历史案例以区分候选原因时检索，可使用“接口 down”“链路抖动”“端口状态”“设备重启”“管理关闭”等中性词并补充实际设备类型。

不得传入接口或自定义时间窗口等未声明参数，不得用知识材料替代运行证据。工具错误或空结果均记录为缺失信息。

## 停止条件

- 无权威告警，或告警无法关联任何资产、接口或可核验的运行证据：停止，结论为 `未知`。
- 已有运行证据但不足以区分候选原因：停止继续猜测，结论为 `疑似` 或 `存在歧义`。
- 不执行 Ping、端口探测、配置读取以外的刷新、设备操作或变更。

## 候选原因与证据

### 物理链路或对端故障

支持：本端明确 down，且对端接口/设备异常或下游同期失联。反对：对端持续正常、无下游影响，或记录显示本端管理关闭。

### 设备重启或掉电

支持：设备离线、启动/重启日志，或同设备多个接口短时间内同时中断。反对：仅单接口中断，且设备运行状态连续。

### 链路抖动

支持：同一时间窗内多次 up/down 切换。反对：只有一次 down，后续无重复切换。

### 管理关闭或配置变更

支持：变更审计、配置日志或明确管理状态记录。反对：管理状态未变且对端或物理层事件先发生。

### 上游或下游故障传播

支持：拓扑相邻节点先故障，随后当前接口或下游资产告警，且时间顺序一致。反对：时间顺序相反或拓扑关系不成立。

## 人工验证与报告

人工验证：核对现场/网管中的端口管理状态与对端状态；核对变更记录；按拓扑确认受影响链路和恢复时间。验证动作由人工在平台外按既有权限执行；除主流程按条件提交报告外，本规程不执行写操作。

报告遵循 `SKILL.md` 的统一报告格式；在摘要标明场景 ID、SOP 版本、权威告警 ID 和观察时间窗。每个候选原因必须带支持与反对证据 ID/时间戳；空结果和工具错误写入“缺失信息”。
